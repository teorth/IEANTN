# IEANTN architecture

The Integrated Explicit Analytic Number Theory Network is a **graph of claims about explicit
analytic number theory, together with a record of how well each one is justified.**

It is not a single formalization project with one build. It is a network in which each node makes
a mathematical claim, declares what it assumes, and carries evidence for the step from its
assumptions to its claim. Different nodes carry very different grades of evidence: a Lean proof
checked by Comparator, an interval-arithmetic computation, or a citation to a paper in the Annals.
The point of the network is not that everything is certain — it is that **for any result you can
read off exactly what it rests on, and how good that evidence is.**

> **Status.** This document describes the target architecture. Sections marked *(planned)* are not
> built yet. Everything else exists in the repository today. See §8.

## 1. The central idea

**Every node's challenge is a conditional theorem. Whether the node itself is justified — by a
Lean proof, by a computation, or by a citation — is metadata, not Lean.**

Three consequences follow, and they are the whole design:

- A node justified by a one-line literature citation and a node justified by a 200,000-line
  machine-generated Lean solution have **identical shape**. Only their metadata differs. So the
  network can hold the literature as it actually is — mostly unformalized — without pretending
  otherwise.
- Nodes never import each other's *proofs*, only each other's *statements*, as hypotheses. An
  unproved upstream node therefore introduces no `sorry` downstream and no build coupling.
- Because the Lean only ever certifies **edges**, the soundness of the **graph** is a separate,
  auditable question. For any conclusion we can compute the transitive set of claims it rests on
  that are not proved in Lean. That report is the repository's headline output.

## 2. The four layers

| Layer | Hand-written? | In the core build? | May import | Purpose |
|---|---|---|---|---|
| **Vocabulary** | yes | yes | Mathlib only | The shared language. Definitions only. |
| **Conclusions** | yes | yes | Mathlib, Vocabulary, other Conclusions | Each node's claims, as named `Prop`s. |
| **Challenge** | **generated** | yes | its own and imported Conclusions | The conditional theorems, sorried. |
| **Solution** | generated / AI | **no** | anything at all | The proof. Verified once, then frozen. |

### Vocabulary

Definitions only — no theorems, no `sorry`, nothing outside Lean core and Mathlib. A theorem here
would be an unattributed claim with no node to own it; every claim belongs to a node.

The Mathlib-only restriction is load-bearing: a challenge transitively imports Vocabulary, so if
Vocabulary reached outside Mathlib no node could ever be spun off as a standalone Palomar
submission.

**What belongs here: anything appearing in more than one node's conclusions.** Something used by a
single node starts in that node's own `Conclusions.lean` and is promoted when a second node needs
it. Promotion is a file move plus an import, and it changes no statement.

### Conclusions

Each node defines its headline results as named propositions:

```lean
/-- Dusart 2018, Proposition 5.4: for every `x ≥ 89693` there is a prime in
`(x, x + x/(log x)³]`. -/
def Dusart2018.proposition_5_4 : Prop := IEANTN.HasPrimeInInterval.logPower 89693 3
```

Use `def _ : Prop`, never `structure`. A `def` unfolds all the way down to Mathlib, so a
self-contained challenge can be generated by substitution; a `structure` cannot be unfolded away
and would have to be emitted into the challenge, where it becomes a definition requiring separate
review. Data-carrying structures are legitimate, but they belong in Vocabulary, where every node
that needs one gets the *same* type — two nodes each defining their own incompatible "record of a
numerical RH verification" could never compose.

**This is the file a human reads.** Because challenges are generated, the docstrings — the informal
statement, the source's numbering, the traps — live here.

### Challenge

Generated from `Conclusions.lean` plus the per-conclusion import lists in `formalization.yaml`:

```lean
theorem Lcm.challenge_not_highly_abundant
    (h : Dusart2018.proposition_5_4) : Lcm.lcm_not_highly_abundant := by
  sorry
```

Because a node's imports are part of the compared theorem's *type*, Comparator's existing guarantee
already covers them: no extra mechanism is needed to stop an import's statement drifting between
challenge and solution. `permitted_axioms` stays at `propext`, `Quot.sound`, `Classical.choice`,
which is what makes a node directly Palomar-shaped.

Imports are declared **per conclusion**, not per node. Different conclusions of the same node
routinely need different assumptions.

The generated challenge doubles as a machine-checkable witness that the yaml's declared graph is
the real one: CI regenerates and diffs, so a hand-edited challenge or a stale yaml fails.

### Solution

May import anything — PNT+, LeanCert, PrimeCert, whatever is convenient. **Each solution is its own
Lake project with its own pinned `lean-toolchain`**, not a library of the core. That is what lets a
solution be verified once and then left alone: without its own pin, the next Mathlib bump would
break every frozen solution in the repository.

Solutions are **not built by core CI**. Core CI builds Vocabulary and Conclusions only, and must
stay fast.

## 3. Justification

Every conclusion records how its implication is justified:

| Kind | Meaning |
|---|---|
| `lean-comparator` | A Lean solution, checked by Comparator against the generated challenge. |
| `numerical` | A computation not currently expressible in Lean (large interval-arithmetic runs, exhaustive searches). |
| `literature` | Proved in a cited source, and accepted on that source's authority. |
| `asserted` | **Claimed in a cited source without proof.** Folklore. |
| `bridged` | Borrowed from another version of the same node, via a bridge proved in Lean. |
| `none-yet` | Claimed here, not yet justified anywhere. A task, not a defect. |

The distinction between `literature` and `asserted` is worth insisting on. `literature` means a
referee-visible proof exists somewhere and we have chosen not to reformalize it; `asserted` means
nobody has written one down. Both are common in explicit analytic number theory and they carry very
different weight, so collapsing them would hide exactly what the network exists to show. Alaoglu
and Erdős writing "it would be easy to see that…" and offering no argument is `asserted`, not
`literature`.

`none-yet` and `asserted` are healthy states. A node whose formalization stalls because the source
paper uses an unproved folklore fact should **surface that fact as its own node** and import it.
That converts a blocked formalization into a well-posed task — and if the folklore fact serves
several papers, the whole network benefits at once.

## 4. Verification receipts *(planned)*

A verification records a **receipt**, content-addressed rather than timestamped:

- the `pp.all`-elaborated statement hash of each conclusion proved;
- the same for each imported conclusion;
- the Lean toolchain and Mathlib revision;
- the pinned Comparator, `lean4export`, NanoDa and Landrun revisions;
- the repository commit, and a timestamp **for display only**.

Staleness is computed by re-hashing, never by comparing dates. The payoff: because the hash is of
the *elaborated* statement, cosmetic edits to an upstream conclusions file — renamed binders,
reformatting, a Vocabulary refactor that unfolds the same way — leave the hash unchanged, and
nothing goes stale.

Receipts are produced by a dispatchable CI workflow, not on a maintainer's machine: a receipt
backed by a pinned workflow with public logs is much stronger evidence than one produced locally.

### Two axes, deliberately not collapsed

- **Broken edge.** An imported conclusion's elaborated statement changed. This is not staleness: the
  verified implication no longer connects to what the upstream node now claims. Binary, fatal. A
  one-character `≤` → `<` scores as trivial on any recency measure and is fatal.
- **Environment drift.** Statements identical, toolchain moved. Graduated, measured in Mathlib
  releases, ages gracefully.

Justification *kind* is a third, orthogonal axis. All three are recorded and displayed separately.
**No single trust score is computed** — a number would hide exactly the distinctions the network
exists to expose.

### Re-running is not re-verifying

Two different operations, which must stay distinguishable in the tooling:

- **Re-run at the recorded pin** — cheap, within budget, but does **not** reduce staleness. It
  confirms the receipt was not fabricated.
- **Re-verify at current Mathlib** — a *port*. Cost is unbounded and unrelated to the original.

On cost: `lake exe cache get` only serves reasonably recent Mathlib revisions. Past that window a
solution's dependencies must be built from source, which alone exceeds the per-node budget several
times over. Staleness is fine, but the cost of clearing it grows **discontinuously**, so a periodic
sweep should keep nodes inside the cache window.

### The one-hour budget

A node's solution should be re-verifiable in roughly an hour. Beyond an operational target, this
gives a **mechanical criterion for splitting a node** — otherwise the hardest judgment call in the
project.

## 5. Refactoring

The network is expected to be refactored continuously: papers get abstracted into reusable
pipelines, folklore gets surfaced, statements get improved. These rules keep that cheap.

### Editing a conclusion, and who gets told

When a conclusion's `Prop` changes, the hash detects it but cannot say whether the *meaning*
changed. An author's declaration cannot settle it either: a declaration is free to write, nobody is
penalised for writing the convenient one, and a required acknowledgement decays into a box to tick.
So the network does not ask for one. The dangerous case is made mechanically impossible instead:

- Editing a conclusion that has **downstream importers or a recorded receipt** is a **hard CI
  failure**, carrying its own fix: `python scripts/ieantn.py new-version <Family>`. *(planned:
  this needs a diff against the base commit, which `check-graph` does not yet do.)*
- Editing a conclusion with neither is silently fine — nothing depends on it, and nothing has been
  verified against it.

This makes versioning the path of least resistance *by construction* rather than by exhortation:
the alternative is a red check, not a form to fill in.

Everything else — new nodes, new versions, bridges — is always allowed, and CI reports the
consequences to the **reviewer** rather than gating the author. That report names the receipts that
went stale, any new unjustified leaves, the blast radius, and the recommended command; it may
suggest a modification, typically *"do not touch `X.v1`; create `X.v2` with a bridge."* It is
advisory precisely because it describes degradation to the author's *own* node's verification
status. Degradation to *other people's* nodes is the hard-failure case above and never reaches the
report. *(the PR comment itself is planned)*

#### Versions, not forks

Nodes are **versioned**: a node lives at `IEANTN/Nodes/<Family>/<version>/` and its id is
`<Family>.<version>` -- `Lcm.v1`, `Lcm.v2`. Versions coexist as ordinary nodes, so restating a
conclusion needs no archiving step, no content-hash naming, and no special status:

1. `python scripts/ieantn.py new-version Lcm` scaffolds `Lcm.v2` from the latest version.
2. Edit `Lcm.v2`'s conclusions -- that is the point of the new version.
3. Justify `Lcm.v2`, either directly or by a **bridge** from `Lcm.v1`.
4. **Downstream nodes do nothing.** They still import `Lcm.v1`, which still exists and is still
   verified. No large solution is re-run.
5. Later, `python scripts/ieantn.py deprecate Lcm.v1 --for Lcm.v2` signals that dependants should
   migrate; once nothing imports it, the housekeeping queue proposes deleting it.

#### Bridges are not imports

A **bridge** is a short Lean file showing that one version's conclusions imply another's. It is
*not* a solution and *not* an import edge, and that distinction is load-bearing: if a bridge
registered as an import, a bidirectional pair of bridges would be an import cycle -- and
bidirectional bridges are exactly what version migration needs.

So there are three relations with three different rules:

| Relation | Acyclic? | What it is |
|---|---|---|
| **imports** | required | trust flows along these |
| **bridges** | not required | lemmas *about* statements; bidirectional is the point |
| **justification transport** (`bridged`) | **required** | whose evidence stands in for whose |

The third condition is not optional. Without it `Lcm.v1` could borrow its justification from
`Lcm.v2` while `Lcm.v2` borrows from `Lcm.v1`: both bridges check, the import graph stays acyclic,
and neither conclusion is justified by anything at all. `check-graph` therefore requires every
chain of `bridged` justifications to terminate at a primitive one.

#### The two directions are different, and CI can decide the classification

Restating `C_old` as `C_new` involves two implications, needed by different parties:

| Implication | Who needs it | For what |
|---|---|---|
| `C_old → C_new` | node `X.v2` | the bridge, so the new conclusion follows from the old |
| `C_new → C_old` | a downstream node `D` | to migrate from `X.v1` to `X.v2` |

Both hold exactly when the two are equivalent — the true **restatement** case, after which the
old version can be deprecated and eventually deleted. If only `C_old → C_new` holds, the new
conclusion is *weaker*: `X.v2` is fine, but downstream nodes cannot migrate, so `X.v1` persists
legitimately and the graph should say so. If neither holds, the change is an **amendment**.

This makes the classification **derivable rather than trusted**: CI attempts both bridges and
reports which succeed. The author's declared classification is a hypothesis that gets checked, not
an assertion that gets believed — which is what makes it safe to let an agent propose it.

### Prefer many small conclusions to few large ones

A node exporting one bundled conclusion invalidates everything downstream whenever any part of it
changes. Several separate conclusions let downstream nodes import only what they use, so a change
to one touches nobody else.

### Keep the Vocabulary surface small

Vocabulary churn is global; conclusions churn is local to a node and its direct importers. That is
why promotion to Vocabulary waits for a second consumer — a tech-debt rule, not tidiness.

### Node identity survives refactoring

When a paper node `X` is generalized into a reusable pipeline `X'`, `X` keeps its id and its
conclusion ids. Its justification becomes a small solution deriving `X`'s conclusions from `X'`, so
`X` now *imports* `X'`, and the old large solution is retired. Downstream nodes do not move.

### Temporary misalignment is expected

Because solutions sit outside the core build, a stale or broken solution is a **data condition**
recorded in the graph, not a build failure. Conclusions may be improved ahead of their solutions,
and the network stays honest about the gap in the meantime.

## 6. The housekeeping queue *(planned)*

The graph **is** the task queue. Because every task below is a derivable property of graph state,
nobody maintains a list: the tooling computes it, and work is scheduled against whatever compute
and AI assistance happens to be available.

| Task | Trigger | Rough cost |
|---|---|---|
| Delete a deprecated version | `X.v1` deprecated, nothing imports it | free |
| Promote a definition to Vocabulary | a second node needs a node-local definition | free |
| Migrate off a deprecated version | `C_new → C_old` verified for its import | one node-sized run |
| Refresh a stale verification | environment drift | one node-sized run |
| Split an over-budget node | its solution exceeds the ~1h budget | moderate |
| Discharge a `none-yet` | — | unbounded |
| Formalize an `asserted` or `literature` node | — | unbounded |

Two things make the queue usable rather than merely long.

**Prioritise by fan-in.** A node's leverage is the number of conclusions that transitively depend on
it. Refreshing one high-fan-in node clears staleness for everything downstream of it, so the queue
should be ordered by fan-in rather than by age.

**One class of task has a deadline.** Most housekeeping is genuinely not urgent — that is the point
of the design, and a graph carrying stale links is working as intended. But **refreshing a
verification before it falls outside the Mathlib cache window is time-sensitive.** Past that window
the solution's dependencies must be built from source, and an hour-long task becomes a day-long one
(ARCHITECTURE §4). Cache-cliff refreshes should therefore be surfaced separately from the ordinary
queue, with the deadline shown.

## 7. Relationship to Palomar

This repository is not a Palomar submission, and most nodes will never be one — the network
deliberately contains axioms, numerical justifications and literature citations that Palomar does
not accept. But every node is kept **Palomar-shaped**, so a certificate can be spun off from any
sufficiently-justified node cheaply:

- challenges are conditional theorems needing only the three logical axioms;
- Vocabulary is Mathlib-only, so a self-contained challenge can be generated by substitution;
- each node carries a `formalization.yaml` validated in CI against Palomar's own contract.

Because imports are per-conclusion and the graph is deterministic, the generator can emit, for any
single conclusion, a challenge whose hypotheses are the **transitive unjustified leaves**, with a
solution composing the per-node solutions along the way — *"the main results of paper X hold given
this RH verification, this table computation, and this folklore lemma."* That is the artifact worth
registering. *(planned)*

## 8. What exists today

- `IEANTN/Vocabulary/` — the shared language. Builds clean; Mathlib-only closure verified.
- `IEANTN/Nodes/Dusart2018/v1/`, `IEANTN/Nodes/Lcm/v1/` — two proof-of-concept nodes and the
  edge between them.
- `scripts/ieantn.py` — the challenge generator, the network checks (import closure, both
  acyclicity conditions, generated-challenge diffing), the dependency report, the housekeeping
  queue, and the `new-version` / `deprecate` commands.
- `scripts/check_palomar_metadata.py` — validates every node against Palomar's *current*
  contract, fetched fresh rather than vendored.
- `.github/workflows/ci.yml` — core build plus the checks above. Does not run Comparator.
- `docs/` — this document and [NODES.md](NODES.md).

Still to build: verification receipts and staleness (§4), the housekeeping queue (§6), the
Palomar spin-off generator (§7), and any solution at all — no node currently carries a
